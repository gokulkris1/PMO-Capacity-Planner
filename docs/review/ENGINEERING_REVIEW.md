## 1. Executive summary (worst first)

1. **Anyone can take over any account, SUPERUSER included, without authenticating.** `POST /api/auth/reset/send-otp` returns the reset code in its JSON response, and `/reset/confirm` then sets a new password (SEC-01). Hotfix today.
2. **Any org-level admin can make themselves platform SUPERUSER or take over another tenant.** `/api/auth/users/invite` accepts `role: 'SUPERUSER'` and an `orgId` from the request body, and it rewrites the role and org of existing users. `PUT /api/auth/users/:id` and `/remove-member` act on users in other tenants (SEC-02, SEC-03).
3. **Tenant isolation is broken in several places.** `qbr.ts` has no authorization beyond holding a valid token: any free sign-up can read, edit, wipe or seed another workspace's QBR data (SEC-04). `/api/debug_db` needs no authentication and returns user emails and roles plus every workspace and membership row (SEC-06). The legacy Express server in `server/` has unauthenticated CRUD over every tenant's data; whether it is still live on Render is unverified (SEC-14).
4. **Production database owner credentials are committed** in 4 scripts and in git history (SEC-05). Rotate the Neon password now; user logins are unaffected.
5. **Saving can lose data.** The workspace GET ignores the selected workspace, but autosave writes to it. The save is a full delete-and-reinsert, and it fires after every load. A user switching workspace can therefore overwrite workspace B with workspace A's data, and concurrent editors silently undo each other (ARC-01, ARC-02).
6. **Authorization is copy-pasted and inconsistent across about 8 functions.** It trusts role and org claims in 7-day, non-revocable JWTs. The role model mixes platform and workspace roles in `users.role`. Plan limits are stored per user, differ between client and server, and are partly client-only. The refresh endpoint the client calls (`/api/auth?refresh=true`) does not exist (SEC-13, UAM-01..03).
7. **The engineering baseline is weak.** There is no lint or format config, TypeScript is non-strict, and no migration tool exists (DDL runs at runtime instead). Three overlapping CI workflows target three hosts, and the Netlify deploy steps are misconfigured. Production dependencies carry 20 vulnerabilities (3 critical). The main bundle is 1.38 MB, and there are no tests for the authorization paths (OPS-01, ARC-03, STD-01..04, SEC-22, ARC-08).
8. **Marketplace readiness** depends on one shared authorization and identity layer: tenant resolved server-side, `cloudId`/`accountId` mapping, and an auth adapter. That layer needs a security headers and CSP strategy that allows framing on `*.atlassian.net`, and a decision on egress and data residency (the Neon project is in `us-east-1` per the leaked connection string). Fixing SEC-02/03/04 through the proposed `_lib/authz.ts` is also the first Marketplace building block.

**Suggested sequencing**
- **P0 (this week):** SEC-01, SEC-05, SEC-06, SEC-02, SEC-03, SEC-04, ARC-01 (hotfix), SEC-09, SEC-10, SEC-14.
- **P1:** shared `_lib` (auth, authz, http, db, env, audit), SEC-07, SEC-08, SEC-11, SEC-12, SEC-13, ARC-02, ARC-03, OPS-01, STD-04.
- **P2:** UAM target model and migration, entitlements, bundle and a11y work.
- **P3:** Marketplace adapters.

## 3. Target UAM model

### 3.1 Roles

| Scope | Role | Who | Notes / legacy mapping |
|---|---|---|---|
| Platform | `PLATFORM_ADMIN` | Orbit staff only | `users.is_platform_admin = true`, granted only through an ops script with an audit row. Replaces `SUPERUSER`. Tenant data access requires a time-boxed `support_grants(org_id, granted_by, expires_at)` row created by an ORG_ADMIN. Break-glass access is audited. |
| Org (tenant) | `ORG_ADMIN` | Customer admins | Billing, org members, create and delete workspaces, all workspaces at WORKSPACE_ADMIN level, org audit log. Legacy `ORG_ADMIN`/`ADMIN`. |
| Org (tenant) | `MEMBER` | Everyone else in the org | No implicit workspace rights (configurable, see UAM-04). Legacy `PMO_ADMIN`/`WORKSPACE_OWNER`/`USER`/`MEMBER` at platform level. |
| Workspace | `WORKSPACE_ADMIN` | PMO lead | Workspace members, integration config and secrets, all data, QBR scenario commit. Legacy `workspace_members.role = PMO_ADMIN`. |
| Workspace | `PLANNER` | PMO analysts, tribe leads | Create, edit and delete resources, projects, allocations, demand and QBR bookings; run imports and syncs; what-if. Legacy `WORKSPACE_OWNER`. |
| Workspace | `CONTRIBUTOR` | Chapter or team members | Read everything. Edit their own craft profile and actuals. Raise marketplace requests (roadmap items 4–5). New role. |
| Workspace | `VIEWER` | Stakeholders | Read-only, export, AI advisor on read data. Legacy `USER`. |

Roles are additive per workspace: one person can be PLANNER in A and VIEWER in B. ORG_ADMIN implies WORKSPACE_ADMIN on every workspace in that org.

### 3.3 Enforcement points

1. **Authoritative: Netlify functions.** Every handler goes through `withApi` → `requireUser` (DB-loaded user, `token_version` check) → resolve the tenant from the resource (`workspaces.org_id`), never from client-supplied `orgId` → `can(actor, action, resource)` from `_lib/authz.ts` → zod validation → handler. Matrix tests cover every row (STD-04).
2. **Data layer (defence in depth).** Every tenant table carries `org_id NOT NULL` and `workspace_id`, and every query filters by `workspace_id`. Phase 2: Postgres RLS on tenant tables with `SET LOCAL app.org_id = $1` inside `withTx`, run as a non-owner `app_rw` role. RLS is supported on Neon; verify interaction with the HTTP `neon()` driver, which has no session state, so it needs `Pool` or a transaction.
3. **Client (UX only).** `GET /api/auth/me` returns effective permissions per workspace, and the UI hides or disables controls using `permissions`, never role-name strings.
4. **Integrations.** Outbound calls run with the workspace's credentials only after `can('integration.run')`. Secrets are never returned, and are cleared on endpoint change (SEC-11).

## 4. Marketplace-readiness notes

What in today's architecture blocks a Forge or Connect app. Statements about Atlassian platform limits should be confirmed against current developer.atlassian.com docs before planning.

- **Tenant model.** Tenants are created by self-service sign-up with a random slug (`org_manage.ts:24-26,143`). There is no install or uninstall lifecycle and no tenant id from the host. Build `tenant_type` plus external ids, provisioning on install, and deletion or retention on uninstall. Tenant resolution must come only from the verified host context, never from `orgSlug`/`wsId` query parameters alone (the root cause of SEC-04).
- **Auth.** The app's own JWT, email/password, OTP, `localStorage` token and `/api/auth/*` do not apply inside Jira. Introduce the `requireUser` adapter (§3.6) so the same authorization core serves SaaS, Forge and Connect. Forge Custom UI talks to resolvers through `@forge/bridge`. The client's direct `fetch('/api/…')` with a bearer token (about 40 call sites) must go behind an `api/client.ts` transport abstraction (ARC-04).
- **Storage and data residency.** The Neon database is in `us-east-1` (connection host in SEC-05). Options:
  - **(a) Forge Remote** to the current Netlify/Neon backend. Requires declaring remote egress. Not eligible for "Runs on Atlassian". Customers needing EU or other residency would need regional databases plus routing by tenant.
  - **(b) Forge-hosted storage/SQL.** A rewrite of the persistence layer, which is easier if ARC-02's per-entity endpoints exist.
  Decide before building.
- **Egress.** OpenAI (`ai.ts:76`), Planview (customer hosts), Resend, Stripe and Clearbit logos (`theme_extract.ts:26`) are all external calls that must be declared in the Forge manifest or disclosed in Connect. Customer-configurable Planview hosts may conflict with static egress allow-lists; confirm whether wildcard or dynamic egress is permitted.
- **CSP and iframe embedding.**
  - Connect pages are framed by `*.atlassian.net`, so the SEC-19 CSP must use `frame-ancestors https://*.atlassian.net` for app routes, and no `X-Frame-Options: DENY`.
  - Forge Custom UI enforces its own CSP. External Google Fonts (`index.html:14-15`, `index.css:5`) and external images need manifest permissions or self-hosting.
  - React inline `style` props set through CSSOM are generally CSP-safe. A `<style>`-injecting library would need `unsafe-inline`; verify.
  - `localStorage` in third-party iframes is partitioned or blocked in some browsers. Keep only UI preferences there.
- **Bundle and performance.** The 1.38 MB bundle (ARC-08) loads inside the Jira chrome. Lazy-load and trim before submission.
- **Timeouts.** The current design assumes Netlify's 10s limit (`integrations.ts:11-12`), and the full-workspace save (ARC-02) does not scale. Forge invocations have their own hard limits. Long Jira or Planview pulls should move to async jobs (Forge async events / scheduled triggers, or a Netlify background function) writing snapshots.
- **Security programme.** Atlassian's Marketplace security requirements for cloud apps (vulnerability management and SLAs, no secrets in source, TLS, data-handling disclosures) make SEC-01…SEC-14 hard prerequisites. Expect a security self-assessment and participation in Atlassian's app security processes.
- **Design.** Align the UI with Atlassian Design System tokens and components. The current token set in `index.css:7-40` already mimics Atlassian blues, but 833 hard-coded colours (A11Y-05) and the emoji iconography (A11Y-01) will need replacing to pass design review.
- **Planview alongside.** Keep Planview as a server-side connector with secrets in a dedicated KMS-style key (SEC-12) or Forge secret storage, scoped per tenant and workspace, with the host lock-down from SEC-11.
